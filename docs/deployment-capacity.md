# 部署容量与附件存储边界

> 最后校准：2026-07-17 | 当前版本：Maildir 本地存储 + 进程内邮件路径索引，不使用对象存储

本文是 MailHub 的服务器选型与附件容量事实源。表中的配置是项目规划基线，不是未经压测的 QPS 或 SLA 承诺。生产容量必须使用真实邮件分布在目标 Linux 服务器上验证。

## 1. 当前部署档位

控制面和数据面建议分机部署。只有验证环境可以把控制面、数据库和 mail-node 合并到同一台机器。

| 组件 | 最低配置 | 推荐配置 | 说明 |
|------|----------|----------|------|
| mgmt-system + MySQL/MariaDB | 2 vCPU / 2 GB RAM / 20 GB SSD / 10 Mbps | 4 vCPU / 4 GB RAM / 40 GB SSD / 20 Mbps 以上 | 最低档仅适合少量管理员和低并发 API；附件代理会同时占用入站和出站带宽 |
| 单个 mail-node | 2 vCPU / 2 GB RAM / SSD / 10 Mbps | 4 vCPU / 4-8 GB RAM / SSD 或 NVMe / 20-100 Mbps | 同机运行 Postfix、Dovecot、OpenDKIM 和 MIME 解析；Maildir 容量按保留期单独规划 |
| Roundcube（可选） | 与 mail-node 共机，共享最低档资源 | 独立 2 vCPU / 2 GB RAM 或计入 mail-node 推荐档 | PHP-FPM 与 IMAP 查询会和附件解析争抢内存及 I/O |

### 1.1 2C2G 最低档的适用边界

2C2G 是低成本可运行基线，不是高并发附件节点。它适用于：

- 管理后台人工查询为主；
- 外部 API 低并发、按需读取；
- 常见附件在 10 MB 以内；
- 不同时执行多份接近邮件大小上限的附件解析；
- Maildir 位于本地 SSD，而不是高延迟网络盘。

部署文档将 Postfix 单封邮件上限设为约 50 MB。enmime 会完整解析并解码目标 EML，因此 2C2G 节点同时处理多个大邮件时会产生明显 GC、延迟抖动和 OOM 风险。若业务无法限制并发，应升级到至少 4C8G，或进入对象存储阶段。

## 2. 当前附件链路及性能边界

```text
Maildir EML
  -> 本地 Message-ID 路径索引
  -> mail-node 完整解析目标 EML
  -> mgmt-system io.Copy 代理
  -> 管理端或外部调用方
```

当前优化解决“每次逐封完整解析”和“目标重复解析”，但仍有以下边界：

| 项目 | 当前行为 | 影响 |
|------|----------|------|
| 索引 | 进程内、有界 LRU，不持久化 | 命中为 `O(1)`；节点重启后的首次请求需要 `O(N)` 邮件头扫描 |
| MIME | 目标 EML 由 enmime 全量解析 | 首字节必须等待目标解析完成，峰值内存随邮件大小和并发增加 |
| 代理 | mgmt-system 使用 `io.Copy` | 不缓存完整附件，但控制面承担一进一出两段流量 |
| HTTP 能力 | 当前无对象级 Range、ETag、CDN | 大文件断点续传和跨地域分发能力有限 |
| 预览 | 图片/PDF/文本预览上限 10 MB | 浏览器会把预览内容读为 Blob；不适合超大附件在线预览 |
| 超时 | mgmt 到 mail-node 的附件请求总超时 60 秒 | 内网拥堵或极慢磁盘可能中断大附件下载 |

不要通过更换 `io.Copy`、增大复制缓冲区或改用 gRPC 解决这些问题。主要成本位于 MIME 解码、磁盘读取和控制面双段网络流量。

## 3. Maildir 磁盘规划

数据面至少按以下公式估算可用空间：

```text
Maildir 可用空间 >= 日均原始邮件写入量 x 保留天数 x 1.3
节点磁盘总空间 >= Maildir 可用空间 + 20 GB 系统/日志余量
```

`1.3` 用于覆盖 Maildir 元数据、临时文件、流量波动和清理调度间隔，不代替备份容量。运维要求：

- 持续监控磁盘使用率，建议 70% 告警、80% 阻止继续扩容邮箱；
- Maildir 使用本地 SSD/NVMe，避免 NFS 等共享文件系统改变 Maildir 原子 rename 语义；
- 日志与 Maildir 最好分卷，避免日志突增挤占收信空间；
- 容量规划同时包含 `.trash` 保留窗口。

## 4. 必须扩容或进入对象存储阶段的信号

出现任一情况时，不应继续把 2C2G 本地解析方案当成最终架构：

- 外部系统开始批量或重复下载同一附件；
- 附件流量影响管理后台、健康检查或控制面 API；
- 需要 Range、断点续传、CDN、跨地域访问或对象级审计；
- 大附件并发导致 mail-node RSS、GC 或 p95 首字节时间持续升高；
- Maildir 备份窗口、磁盘扩容或节点迁移已无法满足恢复目标；
- 需要附件去重、病毒扫描、独立生命周期或不可变保留策略。

## 5. 后续 MinIO 版本的项目基线

以下是 MailHub 计划采用 MinIO 时的项目部署基线，不是 MinIO 软件能够启动的绝对最低值。正式开发时必须根据选定 MinIO 版本重新核对官方支持矩阵。

### 5.1 验证环境

| 项目 | 基线 |
|------|------|
| 节点 | 单节点，仅用于功能验证，不提供高可用 |
| CPU / 内存 | 4 vCPU / 8 GB RAM |
| 磁盘 | 至少 1 块独立 SSD/NVMe 数据盘，不与 Maildir 共卷 |
| 网络 | 1 Gbps 内网 |
| 容量 | 对象使用率控制在 70% 以下，并预留 Maildir + 对象双写空间 |

### 5.2 生产起步基线

| 项目 | 项目建议 |
|------|----------|
| 故障域 | 4 个独立存储节点；MinIO 不与 mgmt-system、MySQL 或 mail-node 混部 |
| 单节点 CPU / 内存 | 8 vCPU / 16 GB RAM 起 |
| 单节点磁盘 | 4 块同规格、直接挂载的数据盘，使用 XFS；不使用 NFS/共享盘作为后端 |
| 网络 | 存储节点之间 10 Gbps；业务接入至少 1 Gbps，并配置独立负载均衡/TLS 入口 |
| 容量水位 | 正常运行不超过可用容量的 70%，同时预留修复、版本和生命周期清理空间 |
| 运维 | 节点/磁盘告警、对象校验、版本控制策略、生命周期、备份和恢复演练 |

该生产基线的目的，是让对象存储真正提供高可用和稳定吞吐。如果只有一台 2C2G 服务器，把 MinIO 与邮件服务混部只会增加内存、磁盘和故障域竞争，不能获得对象存储架构的主要收益。

## 6. MinIO 版本的开发边界

后续版本应采用以下迁移顺序：

1. 保持 Maildir 为邮件事实源，新增附件对象元数据表。
2. 收件后异步提取附件，按 SHA-256 或等价内容哈希写入 MinIO。
3. 校验对象大小和 checksum 后标记可读；失败任务可重试且不阻塞收信。
4. 管理端继续支持受鉴权预览；外部调用方改用短时预签名 URL。
5. 先双写/双读和回填历史附件，再按指标切换默认读取路径。
6. 邮件 purge、回收站恢复和 MinIO 生命周期通过补偿任务保持最终一致。

MinIO 版本完成前，当前本地索引方案是低资源部署的正式路径，而不是未完成的临时旁路。

## 7. 上线前容量验证

至少覆盖以下矩阵：

- 邮箱邮件数：10、1,000、10,000；
- EML/附件大小：1 MB、10 MB、接近部署上限；
- 并发：1、2、5、10；
- 缓存状态：索引命中、mail-node 重启后冷查找、`new -> cur` 后失效重建；
- 指标：p50/p95/p99、首字节时间、总吞吐、mail-node 峰值 RSS、GC pause、磁盘 IOPS、mgmt 双向带宽。

压测结果应回填本文，再据此定义单节点并发限制和扩容阈值。
