# Maildir 邮件路径索引与单次解析设计

> 版本：v1.0 | 日期：2026-07-17 | 状态：已实现、测试并发布

## 1. 背景

当前邮件正文和附件接口以 `Message-ID` 定位 Maildir EML。旧链路每次请求都会扫描邮箱 `new/`、`cur/`，按修改时间排序，再逐封执行完整 MIME 解析；附件端点找到目标后还会再次解析目标 EML。

这使附件下载的控制面二进制代理虽然是流式的，首字节延迟和 mail-node 内存消耗仍受以下因素影响：

- 邮箱中的邮件数量；
- 排在目标之前的 EML 总大小；
- 目标 EML 及其全部 MIME part 的解码大小；
- 同时进行的正文、预览和附件请求数。

当前服务器以 2C2G 裸机为最低部署档，不引入 MinIO、Redis、Elasticsearch 或新的常驻数据库服务。本阶段用有界的进程内路径索引消除主要重复工作。

## 2. 目标与非目标

### 2.1 目标

1. 将索引命中的邮件定位从逐封完整解析降为一次哈希查找和一次文件校验。
2. 缓存未命中时只扫描邮件头；正常 EML 只有目标邮件执行完整 MIME 解析。
3. 附件下载和预览请求不再通过 `findMessage()` 完整解析目标后再解析一次。
4. 索引并发安全、有容量上限，并能识别删除、内容变化和 `new -> cur` 路径移动。
5. 保持现有 Message-ID、fallback ID、附件 index 和 HTTP API 契约不变。

### 2.2 非目标

- 不提取或复制附件文件；Maildir EML 仍是唯一内容事实源。
- 不持久化索引；mail-node 重启后按请求惰性重建。
- 不改变 enmime 全量解析目标 EML 的行为。
- 不在本阶段实现 Range、断点续传、CDN、附件去重或 MinIO。
- 不承诺固定 QPS；容量结论必须来自目标服务器上的压测。

## 3. 设计决策

### 3.1 索引内容

每条记录包含：

```text
(canonical mailbox, normalized Message-ID)
    -> relative/absolute Maildir path
    -> file size
    -> file mtime
```

- 邮箱域名统一小写，本地部分保持原样，与现有 Maildir 路径规则一致。
- Message-ID 继续沿用现有去除首尾空白、`<>` 和引号的匹配语义。
- 文件大小和纳秒级 mtime 是命中校验指纹；Maildir 邮件内容按规范视为不可变。
- 索引采用 LRU，默认最多保留 10,000 条，避免查询大量邮箱后内存无界增长。

### 3.2 写入时机

索引由以下请求顺带预热，不启动全盘后台任务：

- 邮件列表成功解析某一页时，记录该页每封邮件的 Message-ID 和路径；
- 正文、删除或附件请求冷启动扫描邮件头时，记录发现的 Message-ID 和路径；
- 目标完成完整解析后，用解析结果再次校准索引。

这样不会增加常驻扫描任务，也不会让节点启动时间随 Maildir 容量增长。

管理后台和外部 API 最终共用这些 mail-node handler。外部调用方先查询列表、再按 Message-ID 拉正文或附件时，会直接复用列表预热的索引；该优化不要求调用方修改 URL、权限或响应解析逻辑。

### 3.3 查找流程

```text
请求 Message-ID
  -> 查询本地 LRU
  -> 命中：校验 path + size + mtime
       -> 有效：直接打开目标 EML
       -> 无效：删除条目并进入冷查找
  -> 未命中：扫描 new/cur
       -> 只读取 RFC 5322 邮件头并建立索引
       -> 定位目标路径
       -> 仅目标 EML 进入 enmime 完整解析
```

邮件头严重损坏且标准库无法读取时，为保持兼容性，只对这些异常文件使用原完整解析作为兜底。正常路径不会完整解析非目标邮件。

### 3.4 失效与并发

- 文件被删除：`os.Stat` 失败，条目失效。
- 文件内容变化：size 或 mtime 变化，条目失效。
- `new -> cur`：原路径不存在，冷查找在新路径重新登记。
- mail-node 重启：索引为空，第一次请求执行邮件头扫描。
- 并发命中：LRU 操作由互斥锁保护，文件解析不持有索引锁。
- 并发冷启动：冷扫描串行化，避免多个请求同时扫描同一批 Maildir 文件。

## 4. 性能边界

优化后的预期复杂度：

| 场景 | 邮件定位 | 完整 MIME 解析 |
|------|----------|----------------|
| 索引命中 | `O(1)` + 一次 `stat` | 仅目标 EML 一次 |
| 重启后首次冷查找 | `O(N)` 邮件头扫描 | 仅目标 EML 一次 |
| 异常邮件头 | `O(N)` 扫描 | 仅异常文件兜底 + 目标 |

索引不解决 enmime 对目标 EML 的全量解码。大邮件请求仍会占用与解码后 MIME 内容同量级、通常更高的瞬时内存；并发请求的内存压力仍近似线性增加。详细部署边界见[部署容量与附件存储边界](../deployment-capacity.md)。

## 5. 后续 MinIO 演进

MinIO 版本应作为独立存储阶段开发，而不是替换本索引：

1. 收件后异步解析一次，将附件按内容哈希写入 MinIO。
2. 数据库保存对象 key、etag、大小、类型、原文件名和邮件关联。
3. 外部调用方使用短时预签名 URL，附件字节不再经过 mgmt-system。
4. Maildir 保持邮件事实源，迁移期支持双读和校验后切换。
5. 删除、保留期、回收站和对象生命周期必须形成一致性补偿任务。

进入该阶段的容量条件与服务器基线见[部署容量与附件存储边界](../deployment-capacity.md)。

## 6. 验证要求

1. 索引命中后能够在原文件存在且未变化时直接返回路径。
2. 删除、覆盖和 `new -> cur` 后不会继续使用旧路径。
3. 同一邮件的正文、下载、预览保持附件 index 和字节一致。
4. fallback ID 和 Message-ID 规范化语义不回归。
5. `go test ./...` 与 `go test -race ./internal/handler` 通过。
6. 后续在 Linux 目标机补充不同邮件数、附件大小和并发数的基准，记录 p50/p95、首字节时间、峰值 RSS 和 GC。

本次 Windows 构建环境已使用 MSYS2 GCC 16.1 和 `CGO_ENABLED=1` 通过两个 Go 模块的全量 `-race`，并通过普通全仓测试、静态检查和 Linux amd64 交叉构建。
